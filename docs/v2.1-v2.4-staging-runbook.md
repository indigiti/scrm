# SchoolFlow v2.1–v2.4 Staging and Deployment Runbook

Source: PR #47. Cloudways/DigiOps release requires a green GitHub workflow, operator acceptance, and independent private-data backup verification. **Do not deploy a source ZIP to public_html**. Build via \`php tools/build-digiops.php\` and deploy only the generated \`dist/digiops-release\` payload.

## Release contents

- **v2.1**: protect unrelated family profiles during demo clearance; CLI-only staging reset and read-only store consistency audit.
- **v2.2**: \`GET /scrm/api/schools/{school}/work-queue?limit=100&offset=0\`, permission-scoped prioritized leads; My Work interface.
- **v2.3**: campus-specific AI restrictions for unverifiable fees, age, board, transport and availability; school-admin-only \`GET /scrm/api/schools/{school}/public-chat/quality\`, last-source coverage summary. This is NOT an empirical model accuracy score. Existing school-approved knowledge publishing and human review remain required.
- **v2.4**: signed email and WhatsApp delivery webhooks; notifications are updated only after verified provider events. Existing outbound automations remain opt-in and consent-gated.

## Staging data reset: keep \`in.stg.adm\`

A reset **destroys other users, schools, enquiries, tasks, settings and API-key mappings in that staging store**. It never deletes WordPress or external provider records. Stop form submissions and automation workers first.

Confirm the correct Cloudways application/path; production data cannot be inferred from directory naming. Make an off-host, encrypted backup of \`private_html/scrm/data\` (the JSON store AND both key files, if present), then complete a restore drill on a disposable environment.

\`\`\`bash
php bin/verify-store.php --data-dir=/ABSOLUTE/STAGING/private_html/scrm/data --strict
php bin/reset-staging.php --data-dir=/ABSOLUTE/STAGING/private_html/scrm/data --keep=in.stg.adm
\`\`\`

Verify the preview identifies exactly the account to preserve. Record its SHA-256 fingerprint. In that **confirmed staging private directory only**, create \`.staging-reset-authorization\` containing exactly \`stage.digiti.in\`. This marker and environment setting are operator safeguards, not proof of server identity.

\`\`\`bash
SCHOOLFLOW_STAGING_RESET=stage.digiti.in php bin/reset-staging.php \
 --data-dir=/ABSOLUTE/STAGING/private_html/scrm/data \
 --keep=in.stg.adm \
 --expected-sha256=ACTUAL_64_HEX_FINGERPRINT \
 --confirm=RESET-STAGING-KEEP-ADMIN --execute
\`\`\`

Re-run the verifier, confirm one retained account, one NEW empty Admin school, no historic enquiry/user sessions, and successful fresh login with the original password. Removed staff sessions must no longer work. Remove the authorization marker. A private backup folder is created in the data directory; move its contents to approved off-server protected storage and apply retention rules.

## Work queue acceptance

The API requires the existing bearer session and current school membership. Counsellors can only see assigned leads; Admin/Admissions see school-visible leads. Terminal and demo leads do not appear in the smart queue. Confirm due follow-ups, open task reconciliation, first-contact SLA, unassigned records and visit dates; verify that one lead appears once with multiple reasons. Test pagination. The interface is in **My Work**.

## AI quality acceptance

The published school knowledge must be reviewed by the correct school Admin; an uploaded but unpublished knowledge file cannot authorize an answer. Evaluate at least 20 representative questions per campus and academic year, including age cutoff, grade/fee tables, missing transport routes, CBSE affiliation, ambiguous messages, irrelevant prompts and contact consent. Any uncertain campus-specific fact should be clarified or escalated to school admissions. The AI quality dashboard reports *the most recent source per topic*, not a historical accuracy measurement or a calibrated confidence percentage. Existing anonymous topic reporting has no raw private conversation transcript.

## Provider webhook setup: opt-in, server-only

Every configured school has a stable numeric \`school_id\` and may use a UUID route identifier. Provision the following environment variables on the Cloudways PHP runtime (not in GitHub, WordPress HTML or a browser). Replace \`N\` with the target school's **actual numeric ID**:

| Provider | Server-side environment variable | Value |
| --- | --- | --- |
| Resend | \`SCHOOLFLOW_RESEND_WEBHOOK_SECRET_N\` | The matching endpoint's \`whsec_...\` signing secret from Resend |
| Meta | \`SCHOOLFLOW_META_WEBHOOK_APP_SECRET_N\` | The matching Meta app's secret |
| Meta | \`SCHOOLFLOW_META_VERIFY_TOKEN_N\` | A strong, independently generated verification token registered with Meta |

Configure provider endpoints (replace base URL and school ID with actual values):

- Resend: \`POST https://stage.digiti.in/scrm/api/webhooks/resend/N\`
- Meta: \`GET/POST https://stage.digiti.in/scrm/api/webhooks/meta/N\`

Meta GET subscription challenge is returned as text only when the server-side verification token matches. Incoming POSTs are verified using the *raw body*: Resend Svix ID, timestamp and HMAC with a five-minute timestamp window; Meta \`X-Hub-Signature-256\` HMAC. Invalid signatures are rejected. The handler processes supported delivery states only and matches the provider message ID AND school before updating an attempt/queue. Unrecognized webhook payloads are acknowledged without creating a lead. Statuses are monotonic; accepted is never reported as delivered without provider evidence.

Do not confuse Meta access tokens with App Secrets or verify tokens. Live provider webhooks must be independently verified in staging with opted-in test recipients, including duplicate, tampered, delayed, unknown message IDs, and out-of-order events. If Cloudways does not expose PHP environment variables to web workers, configure them with an approved secret store and verify they are readable by PHP *without printing them*.

GitHub Actions additionally runs the original SchoolFlow regressions and front-end checks. Before production rollout verify with real roles on desktop/mobile: admin login and recovery, school isolation, intake from WordPress/one-script, chatbot source accuracy, inbox consent, email/WhatsApp template acceptance vs delivery, job worker replay, document checklist, backup restore, load-test profile, logs, and rollback. A green source CI is **not** a Cloudways acceptance test.

## Known release gates not yet complete

This PR does not implement TOTP MFA, full browser-based acceptance for every role, a per-turn model evaluation dataset, a calibrated AI accuracy score, a browser-editable webhook-secret UI, a MariaDB adapter, or measured concurrent-user Cloudways performance. Real provider delivery, authenticated staging smoke checks, live restore and production rollout require operator access. Keep the source PR separate from deployments and destructive data maintenance.
